# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Brazilian stock/day-trade technical analysis tool ("Day Trade SMC"). It combines Smart Money Concepts (SMC), Price Action, Moving Averages, and VWAP readings into a confluence score, exposed as a Streamlit web app, with the signals it produces persisted and scored for hit rate. All comments, docstrings, UI text, and commit messages in this repo are in Portuguese — match that when editing existing files.

## Two things to know before editing anything

**1. The Streamlit app is in maintenance, not frozen (revised 2026-08-11).** The 2026-08-10 rule said "no new UI"; it was overtaken the next day by the signal-tracking screens and then by a full navigation/layout redesign, so it no longer described the repo. The rule that actually holds: **new analytical capability goes to the agents platform** (`../../agents-runtime` + `homelab/applications/agents/`), which consumes this repo through the API — the app is not where new engine features land. Fixing, restructuring and de-densifying the existing screens is in scope; growing a seventh screen that duplicates something an agent should do is not.

**2. `backend/api.py` is now an agent interface, not just an HTTP API.** Its `/openapi.json` is snapshotted into `homelab/applications/agents/configmap-agentgateway-openapi-acoes.yaml` and converted to MCP tools by the agentgateway. Concretely: `operation_id` is a **tool name** and `description` is the text a model reads to decide whether to call it — renaming either is a breaking interface change, not a cosmetic edit. `include_in_schema=False` on a route means "not a tool", never "not a route": those routes are still served and supported (see the reason next to each). Full contract in the comment block at the top of `api.py`.

See `docs/homelab-pipeline.md` for the full design and implementation status of the homelab MT5 data pipeline (`backend/`, `scraper/`) mentioned throughout this file.

## Repository layout

- `daytrade_smc.py` — the entire analysis engine (~2,530 lines), plus a small CLI that prints a one-symbol report. No UI code lives here: the Tkinter GUI was removed in the 2026-08-06 cleanup, since the Streamlit app had superseded it. `streamlit_app.py` intentionally only imports from this file rather than duplicating logic.
- `streamlit_app.py` — the web UI layer. Imports functions/constants from `daytrade_smc` and renders charts (Plotly), signal panels, the Scanner, and the retro-check screen. Contains no analysis logic of its own. Seven routes under four nav groups since the 2026-08-11 redesign (`/`, `/scanner`, `/ativo`, `/retroativa`, `/acompanhar`, `/assertividade`, `/ordens`) — see "Streamlit-specific gotchas" for why the route lives in the URL path.
- `.streamlit/config.toml` — the theme. Not cosmetic: it declares the dark palette `build_chart` had always assumed, and `Dockerfile.streamlit` needs its own `COPY` line for it to reach k3s.
- `requirements.txt` — cloud-safe dependencies (Streamlit Cloud runs on Linux).
- `requirements-local.txt` — Windows-only extra (`MetaTrader5`, a DLL binding). Never merge this into `requirements.txt` — installing it on the Linux cloud deploy breaks the build.
- `daytrade_symbols.json` (generated at runtime next to `daytrade_smc.py`, not committed) — persisted watchlist, written by `save_symbols`/`load_symbols`, used only when `ACOES_API_URL` isn't configured. On Streamlit Cloud this resets on every redeploy since the filesystem isn't durable.
- `backend/` — the FastAPI side of the homelab pipeline, built as one image (`acoes-backend`) with **four entrypoints**, chosen per-workload via `command:`: `processor.py` (write path — `POST /candles`, plus `GET /watchlist` for the scraper), `api.py` (read path — `GET /candles`, `GET`/`PUT /watchlist`, `GET /status`, `POST /analisar`, plus `/profiles` and `/signals`), `analyzer.py` (the signal worker — sweeps the watchlist writing `signals`, then evaluates pending outcomes; also has a one-shot `--backfill` that reconstructs signals from the candles already stored), and `migrate.py` (applies `schema.sql`, run as an ArgoCD PreSync hook). `db.py`, `models.py`, `auth.py` and `candles.py` are shared — `candles.py` holds the two candle readers the engine consumes, extracted from `analyzer.py` in 2026-08-10 when `POST /analisar` came to need the same thing. Reuse them rather than writing a third reader: the "drop the still-forming candle" guard in `ler_candles` is the trap that would silently poison the whole hit-rate dataset if duplicated and then diverged. Keeping the migration in the same image as the app is what stops schema and code drifting apart between deploys. The image builds **from the repo root** (`docker build -f backend/Dockerfile .`) because `analyzer.py` runs the engine, and `daytrade_smc.py` lives outside `backend/`.
- `scraper/` — runs continuously on a Windows VM alongside a logged-in MT5 terminal, polling `daytrade_smc.fetch_ohlcv(..., source="MetaTrader 5")` and POSTing to `backend/processor.py`. The only component that does **not** run in k3s (it needs the MT5 Windows DLL). It is now the **sole caller** of `source="MetaTrader 5"` — see the `DATA_SOURCES` note below before touching that branch.
- `Dockerfile.streamlit` — image `acoes-streamlit`. Installs only `requirements.txt`: no MetaTrader5, and **no Postgres driver**. The app reaches data exclusively through the `api` service over HTTP; the absence of `psycopg` here is the guard that keeps that decoupling from silently regressing.
- `Makefile` + `scripts/init-tenant-db.sh` — the release path. There is no registry: images are built locally and imported straight into the k3s containerd (`docker save | sudo k3s ctr images import -`), then the tag is stamped into the manifests. **The Makefile must never gain an `apply` target** — see its header for the measured incident behind that rule.
- Kubernetes manifests do **not** live in this repo. They are in the `homelab` repo under `applications/acoes/`, delivered by ArgoCD.

No test suite or lint config exists in this repo.

```

```

## Architecture: the data sources

`fetch_ohlcv(symbol, timeframe, count, source)` in `daytrade_smc.py` dispatches on `source`. **`DATA_SOURCES` is the UI menu, not the dispatch table** — the two deliberately differ, and conflating them breaks the pipeline:

1. **"Homelab (API)"** (`_fetch_ohlcv_api`) — calls `GET /candles` on the homelab `api` service, which serves what the `scraper/` persisted into the shared TimescaleDB (see `backend/` and `scraper/` above). Near-real-time (the scraper polls every few seconds), and the recommended path. Configured via `st.secrets["acoes_api_url"]`/`["acoes_api_key"]` or the `ACOES_API_URL`/`ACOES_API_KEY` env vars (env vars matter because the container in k3s has no mounted `secrets.toml`), wired into the module-level `ACOES_API_URL`/`ACOES_API_KEY` globals at the top of `streamlit_app.py`. `load_symbols()`/`save_symbols()` also become API-backed (`GET`/`PUT /watchlist`) whenever `ACOES_API_URL` is set, falling back to the local JSON file otherwise. **This source speaks HTTP, never SQL.** It used to connect to Postgres directly with `psycopg`; that was replaced so no client outside `backend/` holds a DB credential. `save_symbols` maps to `PUT /watchlist` (not `POST`) because it has always had replace-the-whole-list semantics, which a per-symbol POST/DELETE pair can't express atomically.
2. **"Yahoo Finance"** (`_fetch_ohlcv_yahoo`) — the fallback: works anywhere, no homelab needed, ~15-20min delayed. H4 candles aren't native to Yahoo, so they're synthesized by fetching H1 and resampling (`_resample_to_h4`), anchored to local midnight (Brasília). It is the only rate-limited source, which is why the Scanner's inter-symbol pause (`_PAUSA_YAHOO` in `streamlit_app.py`) is charged to it **by name** — the guard used to be written as "everyone except MT5", so each new source was born paying Yahoo's toll by default.
3. **"MetaTrader 5"** (`_fetch_ohlcv_mt5`) — **dispatches, but is not in `DATA_SOURCES`.** It's a local DLL binding, not a network API, so it only works on the machine with an open, logged-in MT5 terminal — never the web app, which never runs there. `scraper/scraper.py` is its sole caller and the pipeline's whole ingestion path. Removing this branch because it's absent from the UI menu would silently kill all data collection. **Timezone gotcha (fixed 2026-08-10):** MT5 returns bar times in the server's *local* wall clock as if it were UTC (for Clear, Brasília, UTC-3). `_fetch_ohlcv_mt5` must interpret the epoch as `LOCAL_TZ` and convert to UTC (`tz_localize(LOCAL_TZ).tz_convert("UTC")`) — reverting to a plain `utc=True` reintroduces a 3h shift that silently defeats the `ler_candles` forming-candle guard and makes signals on forming candles. See the runbook in `docs/homelab-pipeline.md` ("O fuso do servidor MT5").

   **Which terminal, and which account (2026-08-11).** `mt5.initialize()` used to be called with no arguments, so it attached to whatever terminal was running under whatever account was logged in — and nothing anywhere recorded which. That stopped being theoretical when a demo account was opened alongside the real one: two `terminal64` instances, no rule for which one feeds the pipeline. Connection now goes through `_mt5_conectar`, driven by four module globals (`MT5_PATH`, `MT5_LOGIN`, `MT5_SERVER`, `MT5_PASSWORD`) injected by the scraper the same way `ACOES_API_URL` is — deliberately *not* imported from `scraper/config.py`, because the Makefile ships the two files separately and a first-party import here would break the VM delivery. All four are optional and empty reproduces the old behaviour.
   `MT5_LOGIN` alone is an **assertion**, not a login: the connection raises if the terminal is serving a different account, because collecting from the wrong one produces candles stored under the same symbol name — indistinguishable from the right ones once written. `MT5_PASSWORD`+`MT5_SERVER` make the terminal actually *switch* accounts, which drops whoever is watching that terminal, so it is not the default. For two accounts at once, `MT5_PATH` must point at two distinct **installations** (or a `/portable` copy): instances launched from the same folder share one data directory (`%APPDATA%\MetaQuotes\Terminal\<hash>`, derived from the install path) and fight over the same config.

Which source the sidebar defaults to depends on config: Homelab when `ACOES_API_URL` is set, Yahoo when not (`source_select` in the session-state block). The top-of-page delay warning is chosen from the selected source for the same reason — hardcoded to Yahoo's text, it announced a 20-minute delay over near-real-time data.

Two sources were removed on 2026-08-06: the `"GitHub (MT5 de casa)"` bridge (it read a `data/mt5_snapshot.json` written by an `mt5_bridge/update_data.py` that never existed in this repo — broken, not merely dormant) and its `.github/workflows/mt5-update.yml`. Don't reintroduce a snapshot-over-git data path; the homelab pipeline is the answer to that problem.

## Architecture: the analysis pipeline

1. `fetch_ohlcv` → raw OHLCV `DataFrame`.
2. `build_context(df)` → a `MarketContext` dataclass: ATR/ATR%, RVOL, volatility bucket, EMAs (9/21/50/200), daily VWAP + slope/distance/rejection, swing highs/lows (`detect_swings`), BOS/CHoCH structure events (`detect_structure`), candle patterns, breakout/retest flags, FVG setup, IFR (`compute_rsi`) plus the Diário's IFR when the caller supplies it (`higher_rsi`).
3. Five independent signal generators consume `MarketContext`, each returning a `Signal` (direction, score, confidence, reasons, alerts, `RiskPlan`):
   - `smc_signal` — structure/BOS-CHoCH/FVG based.
   - `price_action_signal` — candle patterns + breakout/retest.
   - `moving_average_signal` — EMA stack/slope.
   - `vwap_signal` — VWAP distance/slope/rejection.
   - `rsi_signal` — IFR **exhaustion only** (≤10 / ≥90 by default), so NEUTRO is its normal answer. There is deliberately no "approaching the zone" band: a reading that scores outside the extreme is just another trend-follower, which the other four already are.
   - `confluence_signal` — combines the **four structural** readings into one blended read. **The IFR does not vote there** — its NEUTRO default would dilute every score, so it is excluded from the weights. But it did gain a *post-decision* role in the 2026-08-12 upstream port: if it is exhausted (directional) it can confirm (×1.30), contradict (×0.45) or define the direction when the structural vote is NEUTRO (reversal, min score `ifr_piso_score`) — gated per style by `rsi_filtro` (Swing Trade: off). See below.
4. `apply_market_filter` clamps direction/score/confidence based on volatility regime (e.g. low volatility blocks entries entirely; isolated single-modality reads are capped below "confirmed" thresholds).
5. `attach_risk` fills in each signal's `RiskPlan` (entry/stop/targets/RR) — stops come from `structural_stop`/`stop_for_signal`, targets from `alternative_targets` (ATR, Fibonacci, structure, statistical expectancy — the same formulas across all timeframes/styles, they just scale with the data).
6. `analyze(df)` runs the full pipeline for one timeframe; `analyze_symbol_mtf(...)` runs it across the confirmation + context timeframes for one symbol, returning a `MultiTimeframeResult`.

**D1 is analysed first, everywhere.** Its IFR is injected as `higher_rsi` into every other timeframe (`rsi_signal` discounts a reading by 0.55 when the Diário is exhausted the opposite way). `analyze_symbol_mtf`, the `analyzer` worker's sweep and `POST /analisar` all reorder for this — `/analisar` pulls D1 in even when nobody asked for it, the same way it already pulls the confirmation timeframes, so the agent and the UI never disagree about the same candle. The one place that can't: `analyzer.py --backfill` and `check_signal_as_of` walk a single timeframe candle-by-candle, where reconstructing the Diário as-of each past bar would risk peeking at the future. They pass `higher_rsi=None`, so a `'backfill'` row never carries the opposing-timeframe discount that a `'worker'` row does — `origem` is in the dedup key, so the two stay separable.

## Multi-timeframe confirmation & operating style

Two "styles," each requiring a different pair of timeframes to agree before a signal counts as confirmed (`STYLES` dict in `streamlit_app.py`, `DAYTRADE_*`/`SWING_*` constants in `daytrade_smc.py`):

| Style | Required agreement | Context only |
|---|---|---|
| Day Trade | M15 + H1 | H4, D1 |
| Swing Trade | D1 + W1 | H4 |

If the two required timeframes disagree, the final recommendation is forced to NEUTRO even if one timeframe looks strong alone. This is enforced identically in both the individual-analysis badge and the Scanner's "Confirmado" column.

## Mini Índice (WINFUT)

Not a screen of its own since 2026-08-11: **`WINFUT` is just an entry in the asset selector**, and `/ativo` swaps to its timeframes via `_estilo_do_ativo`. Its own timeframes are confirmation M5+M15, context M2+H1 (`WINFUT_*` in `daytrade_smc.py`). M2/M5 were added to `TIMEFRAMES`, `DEFAULT_TF_COUNTS`, `_MT5_TIMEFRAME_MAP_NAMES` and `_ANALISE_COUNTS` for it, and are used by nothing else.

**`"WINFUT"` is a logical name, not a ticker.** `yahoo_symbol` passes it through untouched and Yahoo has no such symbol, so the mode is **Homelab-only** and the UI blocks it on any other source rather than surfacing a confusing "symbol not found". The MT5 contract name is broker-specific and rolls quarterly (`WIN$` continuous vs `WINZ25`); the scraper translates it via `SCRAPER_SYMBOL_MT5`, so the stored series stays continuous across the roll while only the mapping changes.

`SCRAPER_TIMEFRAMES_POR_SYMBOL` exists because the scraper loop is a `symbol × timeframe` cross product — putting M2/M5 in the global `SCRAPER_TIMEFRAMES` would collect them for all eleven stocks too, two extra MT5 calls per symbol per loop for data no stock screen reads.

The sidebar's "Estilo" control is built from `STYLES.keys()`, so the WINFUT style deliberately lives in `_ESTILOS_TODOS` instead; resolve styles through `estilo(nome)`, never `STYLES[...]`, or selecting WINFUT raises `KeyError`.

**Known limit:** the `analyzer` worker does *not* record WINFUT signals on WINFUT's timeframes. Its `CONFIRMACAO` and `TIMEFRAMES_VARRIDOS` are global and Day Trade only, so adding WINFUT to the watchlist gets it swept at M15/H1/H4/D1 with M15+H1 confirmation. Live analysis in the UI is correct; the hit-rate history for the mini index would need per-symbol confirmation in the worker.

## Modality filter

The sidebar "Leitura" selector (named "Modalidade" before the 2026-08-11 redesign; the session key is still `modality_select`) picks which signal drives the recommendation: one specific reading (Confluência/SMC/Price Action/Médias Móveis/VWAP/IFR), or `ALL_MODALITIES_OPTION` ("Todas as modalidades"), which averages the score across the **aggregable** readings (`overall_score`) and takes a majority vote on direction (`overall_direction`, tie → NEUTRO). The Scanner always ranks by this overall score.

## The IFR is a sixth reading, but it aggregates into nothing (almost)

`rsi_signal` is in `MODALITIES`, is selectable, gets its own `signals` rows and its own Scanner column — and it is excluded from **both** aggregates: it does not vote in `confluence_signal` (the confluence is computed over the four structural readings, the IFR only arrives as a post-decision *filter*), and `overall_score`/`overall_direction`/`overall_agreement` filter it out via `MODALIDADES_FORA_DO_AGREGADO`.

That is not tidiness, it is two measured regressions. The IFR is a contrarian exhaustion read that is NEUTRO almost always (0 firings in 20 real series, matching the upstream audit's 0-in-60):

- **In the confluence**, voting diluted every score by ~10-12% while contributing no information, and broke comparability with every row already stored for that modality. The 2026-08-12 port keeps it *out of the vote* for exactly this reason, and only adds it back as a filter that is dormant when it is NEUTRO — so when it does not fire, the confluence is bit-for-bit what it was.
- **In the aggregate**, it was worse: `overall_direction` needs an *absolute* majority, so a reading that never votes raised the bar from 3-of-5 to 4-of-6. Measured: the general direction collapsed to NEUTRO in **9 of 20 series** and the Score Geral fell ~6 points — a silent tightening of the criterion that nobody chose, in the default modality that also ranks the Scanner.

`overall_agreement` filters by the same rule, or the screen would print "3 de 6" next to a direction decided by a 3-of-5 vote. If another non-voting reading is ever added, put it in `MODALIDADES_FORA_DO_AGREGADO` too.

Upstream (`kleverson01/acoes`) reverted its own "IFR in the confluence" decision on 2026-08-12 by removing the IFR from the vote weights and turning it into the filter described above; it still does **not** apply the exclusion to `overall_*`, so it still carries the second defect. We kept both exclusions.

## Streamlit-specific gotchas to preserve

- Session-state defaults (`watchlist`, `symbol_select`, `jump_to_symbol`) are set up **before** the sidebar widgets are created — Streamlit doesn't let you mutate a widget's bound session-state key after the widget exists in the same run.
- `@st.cache_data` wraps the per-source fetch+analyze calls — one fixed function per source (`_cached_mtf_api` at 3s, `_cached_mtf_yahoo` at 60s), never a dynamically decorated one. When adding a data source, follow that pattern rather than caching inside `daytrade_smc.py`. `_ultima_vela` (the sidebar freshness caption, 30s) is cached the same way because it runs on every rerun including auto-refresh ones.
- Auto-refresh on the individual-analysis view uses `st.fragment` (`_auto_refresh_30/60/120/300` in `streamlit_app.py`) so only that panel reruns, not the whole page.
- Analysis parameters cross `@st.cache_data` as a **tuple of pairs** (`AnalysisParams.to_items()`), never as the dataclass and never via a module global. Streamlit's hasher guarantees tuples of primitives; a dataclass either raises `UnhashableParamError` or — worse — gets hashed by identity, which fails silently: switching profiles would keep serving the previous profile's scores for the whole TTL, and the Scanner would rank on them.
- Anything that changes which profile is selected (the save/remove buttons) writes a **pending key** (`perfil_pendente`) and reruns, rather than assigning `perfil_select` directly — the selectbox already exists by then, and Streamlit forbids mutating a widget's key after instantiation. Same shape as the existing `jump_to_symbol`. The profile selectbox also needs its session-state default set explicitly, or it silently selects the alphabetically-first profile instead of `padrão`.
- **The route lives in the URL path, never in a query param** (`st.navigation` + `st.Page` with callables, `position="hidden"`). This is what makes the browser's back button work: page-level back/forward was fixed (streamlit#5293 → PR #6271), while query-param back/forward is still broken (streamlit#13963, open, and specific to apps using `st.navigation` — the URL changes, the rerun happens, and `st.query_params` still returns the stale value). Consequence: `symbol`/`perfil`/`modality` ride in query params for shareable links and are **read but never written** — writing them on change would fill the history with entries that #13963 cannot restore, so back would appear to do nothing. `_ALIAS_MODOS` + `_redirecionar_link_antigo` translate the pre-2026-08-11 `?mode=` links; deleting that map silently sends old shared links to the landing page.
- **Everything runs in one file.** `Dockerfile.streamlit` copies exactly `daytrade_smc.py` + `streamlit_app.py` (plus `.streamlit/`), and `st.Page` accepts callables, so there is no `pages/` directory. `st.Page` callables take **no arguments** — what the sidebar computes reaches them through the module-level `CTX` dict, which is why `st.navigation()` runs *before* the sidebar and `pg.run()` *after* it.
- The nav pills reflect the URL, not session state: `_render_nav` re-seeds `nav_grupo`/`nav_sub` **only when `_nav_url_vista` differs from the current route**. Re-seeding every rerun would erase the user's click before it could be read — on the click's rerun the URL is still the old one, and `st.switch_page` is what changes it. Those two widgets deliberately pass no `default=`, since the key always exists by then and passing both makes Streamlit warn on every rerun.
- **Never `st.tabs` to choose between expensive bodies** — tabs execute every tab's body on every rerun. The Dashboard used to put one profile per tab, so a four-profile setup ran five full watchlist sweeps per widget click; the individual-analysis view nested `expander → tabs → panel` and rendered all five reading panels to show one. Both are now `st.segmented_control`, which preserves the if/else.
- Cards are `st.container(border=True)`, never an HTML `<div>` opened in one `st.markdown` and closed in another: Streamlit renders each element in its own DOM block, so that pattern draws a stray line above and below instead of a border around the widgets.
- `.streamlit/config.toml` declares the dark theme that `build_chart` already assumed (`plotly_dark` on `#0a0e13`). Without it the chart is dark inside a light page. Its colors and the `PALETA` dict at the top of `streamlit_app.py` are the same values — change one, change the other.

## Analysis parameters and signal history

`AnalysisParams` (frozen dataclass in `daytrade_smc.py`) holds ~35 curated engine thresholds. It lives in that file, not a new module, because `Makefile` ships exactly `daytrade_smc.py` + `scraper/{scraper,config}.py` to the Windows VM — a new first-party import would break the scraper silently.

It reaches every scoring/risk function through a single trailing `params` field on `MarketContext`, so those signatures never changed. `scripts/conferir-refactor-params.py` runs two engines over the same series and diffs them field by field. Run it before touching any of those numbers — there is no test suite. It compares signals **positionally** and gives up when the count differs, so a change that adds or removes a reading needs a name-matched comparison instead.

Two couplings to preserve: `normalizacao_score` and `filtro_isolada_score_max` are both 79.0 by construction (an isolated reading is capped at 79 so it normalizes to exactly 1.0), and `alternative_targets`' viability threshold is wired to `rr_alvo_1`.

`from_dict` pads and truncates tuple fields to the default's length. That is load-bearing, not defensive: `multiplicador_concordancia` went from 5 entries to 6 when the IFR arrived, and a profile saved before that with a customised tuple would otherwise `IndexError` the first time five readings agreed — months later, in the worker, on a rare path. (Since the 2026-08-12 upstream port that field was replaced by `multiplicador_proporcao` — a 4-slot tuple indexed by agreement *proportion* bands [<0.49, 0.49–0.74, 0.74–0.99, ≥0.99], because the number of active readings now varies by style, e.g. Swing has no VWAP. A profile carrying the old key simply has it ignored by `from_dict` and falls back to the new default.)

`atr_suavizacao` exists so `params_hash` can tell the two ATR conventions apart. `compute_atr` used a plain rolling mean until 2026-08-10, when it moved to Wilder's smoothing (SMMA/RMA, the MT5/TradingView convention). Since `atr_periodo` stayed 14, without this field the old and new hit-rate rows would have been indistinguishable. `"simples"` reproduces the old behaviour for comparison; it is not an operating mode, which is why it has no sidebar widget. **The ATR reaches further than stops:** `detect_structure` validates BOS/CHoCH against `amplitude/ATR ≥ estrutura_range_min`, so changing the ATR changes which structure events count at all — measured on real B3 series, the two conventions differ by ~8% on average and >20% at the 95th percentile, worst on M15.

`STYLE_RSI_THRESHOLDS` + `params_para_estilo` give Swing Trade 20/80 and Day Trade 10/90, but **only when the profile left both at the default** — a profile that picked its own thresholds wins. `STYLE_CALIBRAGEM` (same function) also applies per-style confluence weights and the `rsi_filtro` switch, again only when the profile left those at their defaults — Swing Trade drops VWAP (weight 0) and turns the IFR filter off. Day Trade and Mini Índice stay pinned to the `AnalysisParams` defaults so the UI and the worker (which never calls `params_para_estilo` and runs Day Trade) agree on the same candle. The style-adjusted params are what the UI hashes and what gets stored, so a Swing signal stays distinguishable from a Day Trade one. The `analyzer` worker never calls this: it is Day Trade only (`CONFIRMACAO` fixed at M15+H1).

`POST /analisar` runs the same engine on demand (it's the tool behind "how does VALE3 look right now?") and deliberately **persists nothing** — consultation is not measurement, and writing there would mix readings nobody traded into the hit rate. Its payloads carry `origem='consulta'`, a value that exists in no row of `signals`, precisely so a response forwarded into `POST /signals` shows up as an anomaly instead of passing for `'manual'`. It also analyses the confirmation timeframes even when they weren't asked for, discarding their readings: without that, asking only for D1 would report `mtf_confirmado=false` because nobody looked, in the same field where false otherwise means the timeframes disagree.

Signals are persisted by three producers — the `analyzer` worker (`origem='worker'`), the UI's "salvar sinal" button (`'manual'`), and the one-shot historical pass `analyzer.py --backfill` (`'backfill'`) — which must emit identical rows, so all three build the body with the single `signal_payload()` in `daytrade_smc.py`. `origem` is part of the dedup key precisely so the three can describe the same candle without colliding, and so real-time measurement stays separable from the reconstructed one. Because the backfill writes old candles with today's `criado_em`, `GET /signals` and `/signals/stats` window on **`candle_time`**, never `criado_em`. Unlike the watchlist and profiles, signals have **no local-file fallback**: a hit rate computed over whichever half a process happened to see is worse than no hit rate. Dedup is the unique index on `(symbol, timeframe, modalidade, candle_time, perfil, origem)`; `candle_time` is always UTC, and building it from the displayed (Brasília) timestamp would silently create a second row three hours off.

## Operator feedback (`signal_feedback`)

The decision a person makes about a signal — ACOMPANHAR, OPERAR, IGNORAR, OPEREI, CANCELEI — lives in `signal_feedback`, one row per decision, **not** a column on `signals`. The table is a history: a signal can be marked ACOMPANHAR and later OPEREI, and "the" feedback of a signal is always the **most recent** row. Everything that reads it resolves that with the same `LEFT JOIN LATERAL … ORDER BY criado_em DESC LIMIT 1` (`_FEEDBACK_LATERAL` in `api.py`) — a `GROUP BY` would answer a different question.

`GET /signals` returns each signal already carrying `feedback` + `feedback_origem`, and both it and `/signals/stats` accept an `acao` filter; `/signals/stats` also returns a `por_feedback` breakdown. That exists because the interesting question is "did I do better on the ones I chose to trade than on the average?", and it is unanswerable while the join happens in the client. Until 2026-08-11 the Streamlit screen fetched signals and feedbacks separately and crossed the two lists in the browser, so the answer was limited to whatever fit inside both pagination limits at once.

**`acao=PENDENTE` is a query value, not a stored one.** No row has `acao='PENDENTE'`; it is how you ask for "nobody decided anything about this signal", and it is also the label `por_feedback` groups those under.

**`feedback_origem='auto'` is not a human decision.** The `analyzer` worker applies the `auto_acompanhamento` rules at the end of each sweep (`aplicar_auto_acompanhamento`), writing ACOMPANHAR with `origem='auto'`. Folding that into `'web'` would destroy the very measurement the feedback exists to enable — the same reason `origem='consulta'` exists on the `/analisar` payloads. Three constraints in that SQL are load-bearing: it only touches signals created **during that sweep** (a new rule must not retroactively invent decisions over resolved history), it skips any signal that already has feedback (a human decision wins), and it uses `NOT EXISTS` rather than `ON CONFLICT` because the table deliberately has no unique key per signal.

Two bugs behind the "everything is pending forever" symptom, both fixed 2026-08-11 and both worth not reintroducing: `save_feedback`/`fetch_feedback` in `daytrade_smc.py` used `requests` without the late `import requests` every other API helper in that file has, so the write path raised `NameError` on every click; and the rules table plus its two endpoints shipped without ever changing `analyzer.py`, so rules were written and never read. The screen hid both behind a bare `except Exception: fb_map = {}` — which is why the acompanhamento screen must never swallow a fetch failure again: "no feedback" and "could not read feedback" render identically and only one of them is a number you can trust.

## Sending orders (`execucao.py`, `executor/`)

The README's old promise — "**Não envia ordens**" — stopped being true on 2026-08-11. It now can, and the whole design is about making that capability hard to trigger by accident.

**`execucao.py` is the only place in the repo that sends an order**, and it lives outside `daytrade_smc.py` on purpose: that file is the analysis engine, and analysis has no side effects on the world. Folding order routing into it would mean every import of the engine also imported the ability to trade. Six guards run in order — master switch (`ORDENS_HABILITADAS`, off by default), account identity (`MT5_LOGIN`), **account type (`MODO_CONTA_EXIGIDO`, "DEMO" by default)**, stop/target coherence against the live quote, volume sized and normalised to the symbol's lot step, and `order_check` before `order_send`. The third is the one that matters: while it says DEMO, this module is incapable of touching real money even if the wrong terminal answers — which is not hypothetical, see the MT5 account note above.

**Guards 4 and 5 exist because of what the very first validation order exposed (2026-08-12), and both were latent from the day sending was built.** A PETR4 signal with modelled entry 41.60 and stop 41.46 filled at 41.78:

- **Position size must come from the price you are about to pay, not the signal's modelled entry.** The old `executor._quantidade` divided by `|entrada − stop|` = 0.14, sized 357 shares, and the real distance at the fill was 0.32 — so the position risked **R$ 128 where the rule asked for R$ 50**, 2.6×. Sizing now happens inside `enviar_ordem_mercado` (`risco_maximo=`), because only the sender sees the quote at the instant of sending; `_quantidade_estimada` survives in the executor purely for the log line and for discarding signals with no plan. The freshness guard bounds this drift but never eliminates it — 15 minutes of a fast market move plenty.
- **Lot rounding goes DOWN when sizing from risk**, unlike the shared `_normalizar_volume`, which rounds to nearest and stays that way for callers passing an explicit volume. Round-to-nearest overshoots the ceiling half the time (156 shares → 200, R$ 50 → R$ 64), and the field is called *máximo*. The exception is when not even one lot fits the risk — an expensive stock with a wide stop, e.g. VALE3 at 74.42 with a 1.49 stop, where R$ 50 buys 33 shares and the minimum lot is 100. There it sends the minimum and logs loudly (R$ 149, 298% of the request), because "this rule silently never trades VALE3" is a worse failure than a larger risk that is written down.
- **A target behind the fill is refused.** That PETR4 order went out with the target at 41.72 — *below* the 41.78 buy fill. Neither the local guards nor the broker's `order_check` objected; the position would close for a guaranteed loss and be recorded as `motivo_saida='ALVO'`. "Hit target" while losing money poisons every rule-vs-rule comparison. The check is against the live quote, not the signal's entry, because a gap at the open puts the target behind the price with a perfectly fresh signal.

Both defects were invisible until the reconciliation started recording `risco_efetivo` and `motivo_saida` — the instrumentation found them on its first real order.

**`SYMBOL_FILLING_*` are literals here, not `mt5.` constants.** The Python package exports only `ORDER_FILLING_*` — the value you *send* — and not the `SYMBOL_FILLING_*` bitmask you *test* against `symbol_info().filling_mode`. Using one for the other type-checks and imports fine, then fails silently: `ORDER_FILLING_FOK` is `0`, and `mask & 0` is always false, so every symbol would fall through to the same default. Values come from MQL5's `ENUM_SYMBOL_FILLING_FLAGS`.

**`executor/executor.py` runs on the Windows VM, never in k3s.** The `analyzer` generates the signals but is Linux, and the MT5 integration is a Windows binary — it can never send an order, however natural that placement looks. Same constraint that created `scraper/`, same delivery by `make`, same market-hours gate.

Three properties of the executor loop are load-bearing:

- **Freshness** (`EXECUTOR_FRESCOR_MINUTOS`, default 15) — a signal on an old candle never becomes an order. Without it, restarting the service after any outage fires a burst of orders for signals hours old at prices that no longer exist, and the worst moment for that is exactly the recovery from a crash.
- **Reserve before send** — the `ordens` row (with `signal_id` UNIQUE) is written *before* the order leaves. Writing it afterwards leaves a window where the order exists at the broker and not in the database; a restart inside that window sends a second order for the same signal. Reserving first makes the worst case an orphan `ENVIANDO` row — visible — instead of a doubled position, which is invisible until the statement.
- **`timeframe` is part of the rule key** — a rule keyed only on (perfil, modalidade) matches the same reading on M15, H1, H4 and D1 and opens four positions in one symbol believing it opened one. So is **`symbol`** (since 2026-08-15): the PK is `(perfil, modalidade, timeframe, symbol)`, with `''` meaning "any asset" so legacy rules kept their meaning. That lets a rule be scoped to one paper, or to a **time window** via `horario_inicio`/`horario_fim` (`TIME`, market-timezone, optional, midnight-crossing allowed) — the executor skips rules outside their window in `_um_ciclo`, and an invalid `horario_*` value blocks sending rather than sending. An asset-scoped rule loses its signal to a "any asset" rule in the same slice when both are active (reserved first, only one order) — by design, not a bug.

`RECUSADA` and `FALHOU` are different on purpose: the first means the local guards stopped it and nothing left the machine, the second means the broker said no.

**The order-writing routes are `include_in_schema=False`, and for a stronger reason than the other hidden routes in `api.py`.** Elsewhere the argument is "a model writing this would corrupt the measurement". Here it is that a place-order tool puts money within reach of generated text. The rules (`/auto-ordem`) and the audit (`GET /ordens`, `GET /ordens/stats`) *are* tools — deciding which profile trades and checking what was sent are exactly the questions worth asking in natural language, and neither fires an order by itself.

## What an order produced (reconciliation, 2026-08-12)

`ordens` used to stop at the send. It now carries the outcome too — `fechado_em`, `preco_saida`, `volume_saida`, `resultado_reais`, `motivo_saida` — **read from the MetaTrader 5 terminal, never derived from `signals.resultado`.** That distinction is the whole point: `signals.resultado` is the outcome of the *signal*, with entry modelled at `preco_fill` (the next candle's open). The order executed at a different price, with a quantity rounded to the lot step, and may have been closed by hand, in parts, or with slippage. Computing "it exited exactly at the stop/target" would invent all three. The gap between `assertividade_sinais` (the engine, on candles) and `desempenho_ordens` (what the broker paid) is the cost of executing, and it is only visible because the two are measured separately.

`execucao.consultar_posicao` does the read and lives in `execucao.py` — which stays *the only place that sends* an order; this one only looks. It's there because the MT5 trading-API conventions and traps are the same, starting with the timezone one.

- **`status` gained no new value.** It is the *send* lifecycle (reserved / left / broker refused / guards blocked); open-vs-closed is orthogonal — a closed order is still `ENVIADA`. Putting FECHADA in that column would force every send-audit query to list two values to mean "it left the machine".
- **`resultado_reais` changes meaning with `fechado_em`.** While that is NULL it is the *unrealised* number, rewritten every reconciliation pass; afterwards it is final and net of commission and swap. One column, one concept ("the position's P&L") — but anything that aggregates must keep them apart, which is why `/ordens/stats` returns `resultado_reais` and `aberto_reais` in separate fields. Summing them announces profit that can still evaporate.
- **The result sums *every* deal of the position**, not just the exit ones: the entry deal has `profit=0` but carries the entry commission. Exit price is volume-weighted, because a partial close produces more than one exit deal and a simple mean would be wrong in proportion to the imbalance.
- **`motivo_saida='MANUAL'` is not a measurement.** A rule whose result came from a hand-closed position was piloted, not measured, and mixing the two corrupts exactly the rule-vs-rule comparison the table exists for. `DEAL_REASON_*` *are* exported by the Python package (unlike `SYMBOL_FILLING_*` above — checked on the VM), so there are no magic literals here.
- **The MT5 clock trap applies to deals too.** `execucao.hora_do_mt5` reinterprets the epoch as the server's wall clock (Brasília) exactly like `_fetch_ohlcv_mt5`. Reading it as UTC shifts everything 3h without breaking anything visible — the dates stay plausible, they just point at the wrong hour, and every per-day report goes quietly crooked. Measured 2026-08-12: VALE3's last three M15 candles of the previous session read as 16:15/16:30/16:45, which as UTC would be 13:15-13:45 Brasília, long before the close. `executor._conferir_fuso` re-checks this on every reconciliation against the row's `criado_em` (written by Postgres seconds before the order left, so true UTC) and logs a warning if the convention ever drifts.
- **Reconciliation runs even with `ORDENS_HABILITADAS` off**, on three triggers: startup (catches what closed while the service was down), once per `EXECUTOR_CONCILIACAO_SEGUNDOS` during the session, and once on the open→closed transition — without that last one, whatever closes in the auction only appears the next trading day. Until 2026-08-14 the argument was simply that reading the outcome of what already left sends nothing; since the stop protection below it *does* write, and the argument is now that the only write it makes can only reduce exposure — which is precisely what you want to keep doing *after* switching the sending off.

## The stop follows the price, in one direction only (2026-08-14)

Until this date the **only** exit the system had was the `sl`/`tp` pair attached to the opening order: the price hit one, or the other, or the position stayed. Nothing in the Python ever touched a position after it opened — no `TRADE_ACTION_SLTP`, no trailing, no breakeven, no time-based exit. The broker honours both levels (of 102 closed orders, 59 exited at `ALVO` and 43 at `STOP`, every one exactly at the price, none `MANUAL`), so this was never a bug — it was an absence, and an ITUB4 sale opened 12/08 made the cost of it concrete: two days open, **+1,86R on paper**, target 0,43 away that the price never reached, and nothing anywhere able to turn that into money. A normal pullback hands back the +1,86R and then charges −1,00R.

One rule, both ends: past `PROTECAO_GATILHO_R` of advance, the stop moves to `PROTECAO_DISTANCIA_R` behind the price. At the chosen 0,8/0,8 the first move lands exactly on breakeven and it is a trailing stop from there. The policy is `execucao.stop_protegido` (pure, no MT5); the mechanism is `execucao.mover_stop`; the glue is `executor._proteger`, inside the reconciliation loop that already holds one MT5 connection per pass and already walks exactly the open positions.

- **The invariant is that the stop only ever tightens.** Never loosens, never moves away from the price, never increases exposure. That is what makes it safe to run with sending switched off, on its own switch (`EXECUTOR_PROTECAO_STOP`, **on** by default — the other broker-writing switches default off because they guard against *opening* a position by accident, which this cannot do). It is enforced against the `sl` **read live from the broker** immediately before writing, not against the database: if a human moved it by hand, the hand wins.
- **`TRADE_ACTION_SLTP` writes both levels.** Sending only `sl` **clears the target** — and the target is the one exit that already worked. The live `tp` is re-read and re-sent verbatim; that is the first thing to check after any deploy that touches this.
- **`ordens.stop` is never rewritten.** It is the level that *left* on the send, and `risco_efetivo`, `resultado_r` and the `por_rr_envio` cut are all derived from it. The R that drives the trail is likewise the original `|preco_executado − stop|`: measuring against the already-moved stop would make the protection chase itself, shrinking R every pass until the position dies on the first oscillation. Where the stop is *now* lives in `ordens.stop_atual` (+ `stop_movido_em`), written every reconciliation pass with the live `sl`, so a stop moved by hand is recorded too.
- **Without that column the measurement lies by omission.** A position closed by the *moved* stop records `motivo_saida='STOP'`, identical to a −1,00R of the original plan. Same defect `risco_efetivo` and `desvio_entrada_r` had: neither existed as a question until something recorded it. The write goes in with `COALESCE(%s, stop_atual)` — the pass that first sees the position closed has no live `sl` to read, and a plain overwrite would erase exactly the level it died on.
- **Rounding is away from the price** (floor on a buy, ceil on a sell), the mirror of `_alvo_por_rr`, and `_arredondar_stop` carries a 1e-9 tolerance because the value passes through it twice (policy, then again after the `trade_stops_level` clamp) and 39,41 is 3940,9999… × 100 — without the tolerance the floor ate a cent per pass. The clamp itself is the `SYMBOL_TRADE_STOPS_LEVEL` trap: a stop closer than that to the price comes back as "Invalid stops" (10016), which says nothing to whoever reads the log two days later.
- **`order_check` only in the dry run** (`EXECUTOR_PROTECAO_SIMULAR`). On the live path it would be one more round trip to validate margin, which a stop change does not alter.

Still absent, and worth stating: there is **no time-based or end-of-session exit**, so an M15 day-trade signal can still carry a position across days — only now protected.

**Validation orders are labelled, not deleted (`ordens.teste`, 2026-08-12).** An order fired by hand to check the plumbing really goes out and really executes — and still measures no rule at all, because a person chose it, not the rule's filter. The first one had to be deleted from the table by hand, which erases an event that genuinely happened and depends on somebody remembering to do the cleanup every time. So it is now a flag, in the same spirit as `origem='consulta'` and `feedback_origem='auto'`: this repo consistently *labels* what must not count rather than hiding it. `GET /ordens` and `GET /ordens/stats` exclude those rows by default; `incluir_testes=true` brings them back. Two consumers deliberately pass it: the executor's reconciliation (a test position open at the broker is an open position, and leaving it out would strand it forever, holding the symbol hostage to the "already has a position" guard) and the notification worker (an event is a fact — you *want* to see on your phone the test order you just fired, marked 🧪; an aggregate is a measurement, and there the test distorts). Anything that lists them next to real orders must mark them, or the label just relocates the problem it exists to solve.

**The day-by-day cut is the only one that shows trajectory (`por_dia`, 2026-08-12).** `/ordens/stats` gained three temporal groupings — `por_dia` (chronological), `por_hora` and `por_dia_semana` — and `por_dia` is the series behind the "Dia a dia" chart on the screen: bars for each day's realized result, a line for the running sum. Every other recorte is an aggregate, and an aggregate cannot distinguish a staircase climbing from an old profit being handed back day after day — the same hit rate and the same total describe both. **One y-axis, both series in R$**: the line is the running sum of the bar, and a second y-scale would let Plotly choose each series' scale independently, turning any crossing into a coincidence of scale wearing the face of a fact. Only the *realized* result is plotted (`resultado_reais` sums closed orders only) — including open positions would make the equity curve change shape by itself on every refresh. The bar's color is redundant with its side of the zero line, deliberately: green/red is exactly the pair the most common color blindness merges, and the position carries the same fact.

**The three temporal cuts group by the day/hour the order was SENT, in Brasília time**, never by when it closed. Two reasons: the recorte's window already filters on `criado_em`, so grouping on another column would make the days stop summing to the total; and an open position has no closing date at all, so it would vanish from the day it was fired. The consequence to state out loud is that a position crossing midnight counts on the day it left — in day trade they coincide. The timezone is not cosmetic here, it is the same trap as `_fetch_ohlcv_mt5` and `execucao.hora_do_mt5`: the whole session (10:00-18:00) falls inside one UTC day, so UTC and Brasília agree *today* and the bug would only appear on an auction crossing 21:00 UTC — verified against a seeded row at `02:00 UTC`, which correctly reports as 23h of the previous day.

**`por_rr_envio` and `por_desvio_entrada` had no reader until 2026-08-12.** They shipped into the API and were never added to `_ORDEM_RECORTES`, so the two cuts that found 40% of the loss in a single band were reachable only by curl. A recorte that exists in `/ordens/stats` and not in that dict is invisible; adding one means adding both.

**The one sanctioned exception to that rule is the whole-table reset (`DELETE /ordens`, 2026-08-12).** Zeroing the base in a tuning cycle is not hiding an order, it is starting to measure again — while the history mixes test orders with rules already discarded, `desempenho_ordens` cannot answer "is *this* rule, as it stands now, making money?". It does not replace `teste`, which remains the right answer for the one-off validation order. Three properties keep the exception honest: `confirmar=true` is mandatory (an accidental `DELETE /ordens` must not wipe the base), an **open position's row survives** unless `incluir_abertas=true` (the executor finds what to close via `GET /ordens?aberta=true` — delete the row and the outcome is never read while the position lives on at the broker), and **`signals` is never touched** — the FK cascade runs signal→order, not the reverse, so `assertividade_sinais` comes through intact and only what the broker paid disappears. The route is `include_in_schema=False` for a stronger reason than the order-writing ones: a delete-the-audit tool in reach of generated text is worse than a place-order one. The UI is the "🧹 Manutenção" block on `/ordens`, rendered at **both** of `render_ordens`'s exits — the clear is global while the filter is local, so it has to be available exactly when the current recorte shows nothing. Clear with the executor stopped: the duplicate guard is the `ordens` row itself (`signal_id` UNIQUE), so a signal still inside the freshness window can become an order again (`_tem_posicao` reads MT5 directly, so the risk is a re-send, not a doubled position).

**`GET /auto-ordem` defaults to active rules only, and must stay that way.** The executor consumes that same route and walks the list without checking `ativo`; flipping the default would quietly put it back to trading on switched-off rules. The `/ordens` screen passes `incluir_inativas=true` explicitly — without it a rule vanishes from the list the moment it is switched off, leaving nothing to click to switch it back on.

The `/ordens` screen (third route of the **📋 Sinais** group) is where this is read, and it is also the one place in the UI that can switch a rule on or off. **Switching off is one click; switching on requires a confirmation checkbox first.** The asymmetry is deliberate: switching off is never the dangerous mistake, while switching on is what makes the executor start sending real orders in that slice, and that must not sit one click away from someone who was just looking at a chart. The screen also refuses to render zeros when a fetch fails — "no orders" and "couldn't read the orders" look identical and only one of them is a number you can trust (the same lesson as the `except Exception: fb_map = {}` in the acompanhamento).

## The signal must reach execution intact (2026-08-12, second measurement)

The first 39 orders lost **R$ 1.369 at 31% hit rate in DEMO, while the *same* slices measured +0,17R and 61% in `signals`** (VWAP · M15 · fine_tuned_v2: 60,9% and +0,168R on paper against 27,8% and −0,515R at the broker). That gap is not the cost of executing. It was one defect with two faces, and finding it required joining `ordens` to `signals` by hand — no query in the system could ask the question.

**The engine models entry at the candle's close; the order fills minutes later at whatever the market is.** Position size had already been fixed for this (`_volume_por_risco`, 2026-08-12) — but the *levels* had not, and `executor._reservar` kept sending `sinal["stop"]` and `sinal["alvo_1"]` verbatim. Measured RR at send: median 1,00 with a range of **0,02 to 7,00**, against a design of 0,8–1,2, and only 9 of 39 orders inside the contracted band.

Both tails kill, in opposite ways, and averaging hides it — the mean drift was ≈0,00R while 11 of 39 orders drifted more than 0,5R:

- **Fill drifts toward the target** → the structural stop ends up one to four cents away (MGLU3 at R$ 0,01, BBAS3 at R$ 0,03). Below 0,6 ATR: **6 orders, 6 stops, −1,00R each — 40% of the entire loss.** The engine already has `stop_minimo_atr` for exactly this, but it is enforced against the *modelled* entry, so the drift erases it silently.
- **Fill drifts away from the target** → the target ends up a cent from the fill, and the position closes registered as `motivo_saida='ALVO'` paying **+0,02R**. Four of the nine wins were noise like that: they inflate the hit rate while paying nothing, which is the precise way this measurement lies.

Grouped by RR at send, the gradient is monotonic and leaves no room for another explanation: `> 2,0` → 0% hit, −1,00R, −R$ 684; `1,3–2,0` → 17%, −0,58R; `0,7–1,3` → 29%, −0,43R; `< 0,5` → 71% hit but −0,15R.

Four changes, in the order they matter:

1. **`analyzer.py` sweeps on the candle's phase, not the pod's.** `while True: … sleep(900)` left the phase wherever the process happened to start, and a candle closing at 10:15 could be written at 10:23 — **8,6 min of average delay, measured over 24h of production**. `_segundos_ate_proxima_vela` now sleeps to just after the next close of the shortest swept timeframe. This is the fix at the source: with the delay in seconds, the modelled levels are still valid when the order leaves. `ANALYZER_FOLGA_INGESTAO_SEGUNDOS` (20s) is **not** slack for safety — `candles.ler_candles` drops the still-forming candle, so waking exactly on the boundary reads the *previous* one and the worker would run punctually while measuring 15 minutes late. Use `-x % passo`, never `passo - (x % passo)`: on an exact boundary the second form sleeps a whole period to land on the *next* boundary with no margin at all. The `INTERVAL_SECONDS` cap bounds the wait, never the margin.
2. **`STOP_MINIMO_ATR` (0,6) refuses at send what the drift un-did.** Guard 4 of `execucao.py`, and distinct from guard 5 (`_conferir_coerencia`) on purpose: that one checks the *side* of the stop, this one the *distance*, and a stop on the correct side one cent from the price passes the former. It only runs when the caller supplies the ATR (`GET /signals` already returns it in `detalhes`) — inventing a ruler from a fixed percentage of price would measure the wrong volatility on every symbol but the calibration one.
3. **`_alvo_por_rr` puts the target back at the contracted distance from the price being paid.** The stop does *not* move: it is structural (`stop_for_signal` derives it from a swing, EMA21 or the 10-candle low) and relocating it to an arbitrary distance from the fill would destroy its justification. The RR comes from the signal's own `r_alvo_1`, not the profile's `rr_alvo_1`, because that is the ratio the engine actually achieved after rounding the target to the tick. Rounding is *away* from entry, matching `attach_risk`. Replayed over the 39 real orders, this collapses RR at send from [0,02–2,88] to **[0,81–1,33]**.
4. **`ordens.desvio_entrada_r` makes the drift visible.** Signed, in R, and never folded into an absolute value — the two tails kill in opposite ways and the mean of the signed drift is ≈0. In R rather than reais or percent because it is the only unit comparable between a R$ 4 MGLU3 and a R$ 74 VALE3. `/ordens/stats` gained `por_rr_envio` and `por_desvio_entrada` for the same reason `risco_efetivo` exists: **both defects were invisible until something recorded them**, and the first query that could ask found 40% of the loss in a single bucket.

**The profiles were calibrated for the wrong metric.** `fine_tuned_v1` runs `rr_alvo_1 = 0,8` and `fine_tuned_v2` `1,0` — targets shortened to raise the hit rate. At 0,8R you must win >56% just to break even, and the orders deliver 50%. Hit rate and expectancy pull in opposite directions here, and "assertividade" names the one that does not pay: calibrate on `expectativa_r`, and read `taxa_acerto` only alongside it. Note the sampling bias when comparing: 28–47% of M15 signals end `EM_ABERTO` and are excluded from every rate, while as orders they become positions that just sit there (10 of the 39). A more distant target grows that slice, so any comparison has to count how many resolve, not only what the resolved ones pay.

## What the parameter sweep measured (2026-08-12)

`scripts/varrer-parametros.py` + `scripts/analisar-varredura.py` exist because the two prior attempts to calibrate this engine were both wrong, and both were wrong in the same way: they trusted a sample too small to say anything. The profiles in production were tuned on "emulação retrospectiva, 7 dias úteis" (see the comment in `deployment-analyzer.yaml`), and the `signals` table — purged on 2026-08-06 — **contains only two days**: `/signals/stats?dias=2` and `dias=90` return the identical 1309 rows. Any per-modality number read off that table is a two-day, single-regime measurement, and "Price Action: 80% acerto" was `n=10`.

The harness runs the real engine over stored candles (10 symbols × 750 M15 candles after warm-up), evaluating with `evaluate_signal_outcome` — the same walk-forward, next-open fill, cost-netted evaluator the worker uses. Two design points carry it:

- **Evaluate inline; never accumulate the future slice.** The first version held one DataFrame slice per signal and was killed by the OOM reaper at 23Gi. Evaluating at the point of generation and keeping only scalars runs the same sweep in **138 MB**.
- **One engine pass, many R/R.** `rr_alvo_1` does not change *which* signals are born — direction, score and stop come from `stop_for_signal` + `stop_minimo_atr` and never read it — only where the target sits. So the same signal is evaluated under every candidate R/R for free. `stop_minimo_atr` *does* change the stop (and therefore the risk, the target, and whether the signal survives at all), so it needs its own pass. Persist per configuration, not once at the end.

**Result 1 — the targets are calibrated backwards.** Over 94.770 evaluations, expectancy rises monotonically with the target while hit rate falls, and the two values running in production are the two worst:

| `rr_alvo_1` | hit rate | expectancy |
|---|---:|---:|
| 0,8 *(fine_tuned_v1)* | 59,7% | **−0,028R** |
| 1,0 *(fine_tuned_v2)* | 55,2% | +0,002R |
| 1,5 | 45,8% | +0,043R |
| 2,0 | 39,4% | +0,077R |
| 3,0 | 31,3% | **+0,146R** |

This is the same conclusion the order data reached from the other end, and it is the whole argument for reading `expectativa_r` rather than `taxa_acerto`: the metric named "assertividade" is maximised at exactly the settings that lose money.

**Result 2 — relative volume predicts the outcome, in the *opposite* direction to the design.** The engine already gates on volume: `candle_patterns` refuses to name a pattern below 1,3× the 20-bar average, and `_confirmed_breakout` checks it too. The natural next step looked like extending that gate to the other readings — and a two-day sample supported it (Médias Móveis at RVOL ≥1,3 hitting 85,2% against 48,1%, on n=27). **The full sweep refutes it.** At `rr=1,5`, and holding at `rr=1,0` and `rr=3,0` alike:

| RVOL | hit rate | expectancy |
|---|---:|---:|
| < 0,8 | 48,8% | **+0,125R** |
| 0,8–1,0 | 45,4% | +0,038R |
| 1,0–1,3 | 44,0% | −0,013R |
| 1,3–2,0 *(the current gate)* | 42,4% | **−0,058R** |
| ≥ 2,0 | 43,5% | −0,025R |

The decline is monotonic into the gate band for Confluência (+0,250R → −0,219R), SMC (+0,052 → −0,174) and VWAP (+0,173 → −0,050), and flat-to-negative for Médias Móveis. Price Action, whose gate places it *entirely inside* the worst band by construction, measures negative in every bucket it occupies here — the "best modality" of the two-day table is the worst of the twenty-nine-day one.

Do not read this as "volume is noise": it is a measured association in one direction, on one market, at one timeframe, and the mechanism is not established. Read it as the reason the gate must not be copied into the other four readings, and as the reason `context.rvol` — computed since forever, printed in the CLI, stored in `detalhes`, and scoring **nothing** — is worth wiring in with a *negative* weight rather than a positive one, after a confirming sweep on a second timeframe.

**W1 is collected since 2026-08-12.** It was excluded from `SCRAPER_TIMEFRAMES` on the argument that a weekly candle need not be resent every few seconds — but D1 is resent exactly that way and changes just as rarely, so the argument never separated the two. Without it `/candles?timeframe=W1` returned 404 and Swing Trade (`SWING_CONFIRMATION_TIMEFRAMES = D1+W1`) was not wrong but *inexistent*. `scraper.py --carga-inicial W1 --velas 150` filled ~3 years for all 15 symbols in one pass; the real-time loop keeps it fresh from there. It does **not** change the sweep cadence — `_segundos_ate_proxima_vela` sleeps to the shortest swept timeframe, still M15 — and `ANALYZER_CONFIRMACAO` stays M15+H1, because changing it would redefine `mtf_confirmado` for every new row while the historical ones kept the old meaning.

Two traps worth keeping: a manual `python scraper.py` on the VM does **not** inherit the NSSM service environment, so `PROCESSOR_URL` silently falls back to `localhost:8000` and every post fails; and `_post_candles` swallows failures by design (the real-time loop resends within seconds), so anything that runs **once** per symbol — the initial load — has to check its return value or it will report success while writing nothing.
